# v0.3 方案：本地工作经验闭环

## 目标与边界

把完成过的重复性任务整理成可复用流程，在下次执行时找回、核对并改进。职业可以不同，专精的环节始终是“经验复用”，而不是代替所有专业工作。

通用机制负责记忆生命周期；领域技能负责实际工作；用户资料与任务证据提供事实。没有任务访问能力或执行工具时，系统只能整理现有材料，不能自行完成观察和验证。

## 三层架构

| 层 | 内容 | 产生方式 |
|---|---|---|
| 通用层 | 检索、核对、执行后沉淀、提炼、失效与冲突处理 | 随 Skill 发布 |
| 场景层 | 输入、步骤、分支、产物、验收和适用边界 | 从实际任务提炼为 workflow |
| 本地经验层 | run 证据、lesson、约定、决策及原有开发档案 | 在授权任务中选择性积累 |

后两层保存在用户工作目录的知识库中，不随 Skill 升级覆盖。不同工作区默认隔离，跨库只检索用户配置的位置。没有中央账号或后台上传。

## 最小闭环

空库正常工作 → 保存有价值的任务证据 → 提炼候选流程 → 下次按条件找回 → 核对并实际执行 → 验收 → 更新流程。

首次完成不能反向声称复用成功。后续成功也不能按次数自动升级；需要核对证据覆盖范围。遇到反例先定位原因，不能直接把错误归结为用户操作。

流程内保持参数与规则分离。日期、路径和输入文件属于参数；计算口径、依赖和验收属于规则。复用记录允许保留差异，不追求把所有任务合成一个模板。

## 记录策略

- 重复任务、明确约定、可复用修复：优先保存。
- 一次性内容、操作流水账：跳过。
- 未验证发现：候选。
- 具体习惯：仅用户明确要求记住时保存为有范围的约定。
- 凭证、敏感原始资料：不复制入库。

原有专用 Project Finder 资料作为来源按需接入，不抹掉 SDK、工程骨架和本地约束。只有通用规则抽象，具体证据保持具体。

## 可靠性设计

稳定 ID、相对路径、任务与流程双向引用、明确状态、来源与验证范围；结构检查工具只读。记录先于索引保存，索引可重建。新格式兼容旧记录，不承诺旧工具能读新格式。

不自动修改 Skill 规则、安装触发器、跨目录扫描、发送成果或删除历史。流程里的外部动作依照当前任务授权执行。

## 验收与后续路线

发布前自动检查：空库、v1 兼容、v2 候选流程、缺失引用、错误路径、循环替代、无成功证据却设 active、失败任务不能支持流程激活、索引预览和只读性。

真实试用另行验证：

1. 用原有开发任务对比原版，观察来源准确性、约定遗漏和适配成本。
2. 用一个非开发重复任务跑两轮，确认第二轮能找到第一轮流程，并发现输入变化。
3. 注入明确环境变化，确认过期流程不再被直接采用。

这些是验收计划，不是已取得的效果。格式与工具测试通过不能证明比原专用版更好用。

先完成真实闭环再考虑更复杂检索、后台触发或跨设备同步；不靠扩大范围替代效果验证。
