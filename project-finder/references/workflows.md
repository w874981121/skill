# 工作流

## 检索与复用评估

1. 将需求拆成业务规则、技术约束、UI 偏好。功能名称相同不代表规则相同，例如每日次数可能由客户端或服务端控制。
2. 在 `index.md` 检索同义词、标签、故障症状和能力标识，再读取候选记录。若索引疑似缺漏，可搜索 `memories/`；索引只是派生导航，不是唯一事实源。
3. 在目标项目与用户提供的来源项目中核对关键文件、调用方、接口契约、状态管理和必要的上下游。用工具支持的文本搜索，优先缩小范围；排除依赖和构建产物。
4. 按业务规则吻合度、运行环境兼容性、依赖可用性、验证证据和适配工作量排序。来源多不代表成熟，不编造评分或工时。
5. 输出最相关候选及其边界。没有合适实现就说明缺口，继续按用户要求实现，不制造不存在的历史经验。

建议输出：

| 能力 | 来源与证据 | 适用条件 | 复用方式 | 需要补齐 |
|---|---|---|---|---|
| 每日打卡 | 项目与关键文件 | 服务端判断日期 | 适配接口后复用 | 新项目的奖励规则 |

只有核对过源代码才能称为已确认来源。无法访问的旧记录可列为线索，但需要说明。

## 实现或迁移

1. 阅读目标项目已有规范和结构；不为迁移而擅自更换框架、状态管理或构建工具。
2. 识别应搬用的最小逻辑边界及必需依赖；不要复制整个旧项目或假设 SDK 可用。
3. 对照输入输出、异常路径、鉴权和副作用进行适配。跨框架时保留业务语义，明确哪些代码实际重写。
4. 针对变更验证关键行为。记录实际执行的检查及结果；没有环境或后端时明确验证限制。
5. 提炼记忆，按 schema 合并或新建。业务未验证不妨碍记录构建结果，但不得扩大结论。

`generate-project` 是兼容入口：只有用户要求新项目时才创建工程；否则接入当前项目。骨架由目标项目或用户提供，无必需的外部 Skill、内部 SDK 或在线服务。

## 分析项目

先看项目说明、依赖声明、入口和相关业务文件；根据用户目标深入。用户要求整体分析时可按模块分批覆盖，并报告实际覆盖范围。

记录业务能力与技术实现，保留不同技术栈的实现差异。功能与 UI 分别描述，但不假设它们可以独立搬用。

静态分析的记录设为 `candidate`，验证证据为 `static`。只有真实执行的验证或可追溯的既有验证证据，才能支持对应的验证描述。不要为每个函数建档。

## 写入与维护

1. 判断是否具有重复使用价值，以及适用范围是项目内还是跨项目。
2. 读取 schema 和同类记录；以能力、实现方式和适用条件比对。
3. 同实现更新来源和证据；重要差异作为新变体。对冲突记录保留双方条件，不能以“最后写入”为正确依据。
4. 先写记录，再更新索引；仅修改本次涉及的文件，保留用户人工备注。写入前复读已存在的目标文件以避免覆盖并行改动；工具支持时采用临时文件替换。
5. 检查索引链接、来源定位、替代关系和状态。失败时如实报告部分写入，后续可从记录修复索引，不能声称全部成功。

读取旧记忆时进行按需刷新，不要求每次扫描整个库。来源已删除或适用条件失效时标记 `stale`，核实后可以恢复；明确被替代的记录使用 `deprecated`。不自动删除历史。

## 旧库迁移

旧版的 `features/`、`ui/`、`chains/`、`projects.md` 可作为只读来源，按当前需求逐步转换：

- 功能档案转换为 `implementation`，保留真实来源和技术依赖。
- 链路转换为记录中的前置条件或关联记录；不把所有链路节点作为强制需求。
- 只有项目名、没有文件证据的记录属于未核实线索。
- 旧档案写着“可运行”不代表已经验证，应补齐依据。

不批量覆盖原库，不把历史 SDK 自动改写成新的 SDK，也不自动同步到任何客户端专属目录。
